Slumber

Terminal-native HTTP client with collection management, chained requests, and environment profiles

A Rust-built TUI alternative to Postman and Insomnia — entirely keyboard-driven, stores collections as plain YAML, and chains responses between requests without scripts.

FRI 22 MAY 2026

★ WHAT IT IS

Slumber is a Rust TUI HTTP client that hit v2.0 this week with a rewritten request-chaining engine. Collections are stored as YAML files alongside your code — slumber.yaml lives in the repo root and commits like any other config. The chaining feature lets you reference a field from a previous response using a simple {{"{{"}} response.login.token {{"}}"}} template syntax, removing the need for pre/post-request scripts. Environment profiles (dev, staging, prod) switch base URLs and auth tokens without modifying requests.

¶ 01 WHY · IT · MATTERS

The GUI HTTP client space is dominated by tools with opaque binary collection formats, cloud sync requirements, and telemetry that leaks request data. Slumber’s YAML-in-repo model means API collections are versionable, diffable, and shareable without a paid team account. The TUI approach eliminates the context switch penalty of a separate GUI app during development. The 2.0 chaining engine is a direct answer to the most common reason developers reach for pre-request scripts in Postman — passing an auth token from a login call into subsequent requests is now a one-liner template.

¶ 02 HOW · TO · TRY · IT ~8 MIN
01

Install: cargo install slumber or brew install slumber. Pre-built binaries for Linux, macOS, and Windows are on the GitHub releases page for those without a Rust toolchain.

02

In your project root, create slumber.yaml with a collection. The minimal structure is requests: followed by named entries with method, url, and optional body. Run slumber to open the TUI.

03

Try chaining: add a login request that returns a JWT, then reference it in a subsequent request header: Authorization: Bearer {{"{{"}} chains.login.body.token {{"}}"}}. Slumber executes the login automatically if the token is not yet in the session cache.

¶ 03 WHAT · TO · OBSERVE

Notice the history panel on the right of the TUI — every request and response is persisted locally in a SQLite file at ~/.local/share/slumber/history.db. This makes reproducing intermittent API bugs significantly easier than with GUI clients that discard response history after a session. Also check the --dry-run flag for inspecting what a chained request will send before it executes — essential when the upstream login call has a rate limit.
