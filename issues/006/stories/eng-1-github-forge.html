If I Could Make My Own GitHub

Mat Duggan diagnoses the pull-request model as the root structural problem in modern software development — and names the VCS, review, and forge alternatives that already exist to fix it.

BY · MAT DUGGAN · MATDUGGAN.COM · 15 MIN READ · ENGINEERING

03 DUGGAN'S RECOMMENDATIONS
5 CHANGES
01

Replace Git with Jujutsu (JJ) as the VCS layer

JJ presents changes as the primary unit rather than commits, making rebasing and stack manipulation first-class operations instead of fragile workflows. It is Git-compatible at the data layer, so migration is incremental rather than all-or-nothing. Duggan argues this single change would remove most of the pain in collaborative rebasing workflows.

02

Adopt Gerrit-style change-based review instead of PR-based review

Gerrit reviews individual changes (commits) rather than batched pull requests. This encourages small, reviewable increments and makes it impossible to hide a complex change inside a "refactor" PR. Google's internal Critique tool uses a similar model and is cited as the productivity baseline Duggan wants to reach externally.

03

Make stacked PRs a first-class primitive, not a workaround

Stacked pull requests — where PR B depends on PR A, which depends on PR C — are currently handled via third-party tools like Graphite or manual branch management. A forge built for high-volume AI-assisted development needs stacking built into the data model, not bolted on, so that dependency graphs are visible and automatically re-ordered when a base branch lands.

04

Self-hostable on commodity hardware — a Raspberry Pi is the target

Duggan's reference point is that a forge serving a 10-person team should run comfortably on a $75 device. This is both a literal resource constraint argument (Forgejo already approaches this) and a philosophical one: if the forge requires cloud infrastructure to function, it has imported the same lock-in problem it was meant to solve.

05

Open governance — no single company controls the forge roadmap

GitHub's roadmap is determined by Microsoft's enterprise sales priorities. Duggan wants a forge governed by its users in the way Forgejo is governed by the Codeberg community. Open governance is the structural guarantee that the forge remains a tool for engineers rather than a platform for extracting enterprise subscription revenue.

04 YOUR FORGE · AUDIT CHECKLIST
5 QUESTIONS
Q1

What is the average PR size (in lines changed) on your team over the last 90 days?

If the median is above 400 lines, your review process is almost certainly batching changes that should be reviewed incrementally. This is the key diagnostic for whether a Gerrit-style model would help your team specifically.

Q2

How often do engineers on your team rebase rather than merge — and how long does a contested rebase take?

High rebase friction is the primary quality-of-life problem JJ is designed to solve. If your team avoids rebasing because it's painful, that's a direct productivity cost Duggan's recommendation addresses.

Q3

Do you have a GitHub outage runbook — and have you needed it in the last 12 months?

GitHub had several significant outages in 2024–2025. If you lack a runbook and your CI/CD is tightly coupled to GitHub Actions, a self-hosted forge backup — even a partial one — reduces your platform risk meaningfully.

Q4

Are you currently paying for a stacked-PR tool (Graphite, gh stack) — and is that a line item you could eliminate with a forge that handled stacking natively?

Third-party stacking tools work reasonably well but represent a band-aid on a structural problem. Native stacking removes a category of edge cases and simplifies your tooling surface.

Q5

Has your PR review throughput kept pace with your code generation throughput since you introduced AI coding tools?

This is the core diagnostic. If AI tools are producing code faster than humans can review it, your bottleneck is now the review model — and a change-based system that makes reviewing smaller increments easier is the structural fix.

05 QUICK START · TRY IT IN 30 MINUTES
3 STEPS
01

Install Jujutsu and colocate it with an existing Git repo

Run brew install jj (macOS) or follow the JJ install guide at martinvonz.github.io/jj. In any existing Git repo, run jj git init --colocate. This makes JJ and Git interoperate on the same repo — you can switch back to pure Git at any time. Spend 15 minutes navigating your commit history with jj log and editing a commit mid-stack with jj edit.

02

Spin up a Forgejo instance locally using Docker

Run docker run -d -p 3000:3000 codeberg.org/forgejo/forgejo:latest and visit localhost:3000. Create a test repo, push a branch from your JJ-managed repo, and open a pull request. Note the UI differences from GitHub and observe how much of your muscle memory transfers.

03

Time a three-level stack: create, review, and land it

Using JJ's stacking semantics (jj new to create a child change), create three dependent changes in your test repo. Push them to Forgejo as three separate PRs with explicit dependency notes. Time how long it takes from creation to "all three merged in order." Compare that against how long the equivalent workflow takes in your current GitHub setup.

06 MENTAL MODEL · TEAM EXERCISE · 30-DAY EXPERIMENT

MENTAL MODEL

The forge is the bottleneck, not the codebase

When AI tools generate code faster than humans review it, the constraint shifts from "can we write it?" to "can we evaluate it?" The pull-request model was designed for the first constraint. It is poorly suited to the second. Duggan's redesign addresses the second constraint directly by making the review unit smaller (individual changes) and the dependency structure visible (native stacking). The mental model shift: your forge is now part of your review pipeline, not just your code storage layer.

TEAM EXERCISE

The PR size retrospective

Pull your team's last 30 merged PRs from the GitHub API. Plot the distribution of lines-changed per PR. Identify the ten largest. For each: could this have been reviewed more effectively if submitted as three or four smaller changes? Count how many times "this PR is too large to review effectively" appeared as a comment. If the answer is more than twice, you have measurable evidence that your review model is costing you quality — and a concrete argument for trialling stacked or change-based review.

30-DAY EXPERIMENT

Run JJ on one project for a month

Pick a single non-critical project and commit to using JJ as the VCS interface for 30 days. Keep Git as the backend (colocated mode). At the end of the month, run the PR size analysis again on that project versus a comparable project using standard Git. Measure: did average PR size decrease? Did rebase conflicts decrease? Did the time from "PR opened" to "PR merged" change? These three metrics will tell you whether the JJ model produces the workflow improvement Duggan claims.
