Cloudflare Workers AI + session affinity: get 20–30 ms tokens and 80% cache hits today

Cloudflare Workers AI now runs on Infire, its custom Rust inference engine, serving Kimi K2.5 at 20–30 ms intertoken latency. One header change — x-session-affinity — routes follow-up requests to the same node and raises prompt cache hit rate from 60% to 80%, cutting effective cost on long-context sessions immediately.

Why it's worth trying: If you're already calling any model on Cloudflare Workers AI, the session affinity header is a zero-cost, one-line change that improves both latency and cost on multi-turn conversations. You're leaving cache hits on the table on every session that doesn't use it. Beyond the header, Workers AI is now the only inference endpoint where Kimi K2.5 is available at sub-30 ms intertoken latency — worth benchmarking if you're currently routing Kimi traffic through other providers.

Access and pricing: Workers AI offers a free tier (10,000 neurons/day). Paid usage is billed per neuron (Cloudflare's compute unit). Kimi K2.5 specifically may carry a different per-token rate — check the Workers AI pricing page for current model-specific costs. No GPU reservation required; cold starts are under 20 seconds.

Quick start — under 5 minutes if you have a Cloudflare account

Add x-session-affinity: YOUR_SESSION_ID to your next Workers AI request. That single header change enables prompt cache reuse across turns. Measure cache hit rate in the Workers AI analytics dashboard before and after.

Step-by-step
  1. Log in to Cloudflare Dashboard → Workers AI. Confirm you have API access and note your account ID and API token.
  2. Make a baseline request to Kimi K2.5 without session affinity and record time-to-first-token and intertoken latency:
    curl https://api.cloudflare.com/client/v4/accounts/{ACCOUNT_ID}/ai/run/@cf/moonshot/kimi-k2.5 \
  -H "Authorization: Bearer {API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{"messages":[{"role":"user","content":"Explain KV cache in one paragraph."}]}'
  3. Now send a follow-up turn with the session affinity header. Use a consistent session ID (any stable string per user session):
    curl https://api.cloudflare.com/client/v4/accounts/{ACCOUNT_ID}/ai/run/@cf/moonshot/kimi-k2.5 \
  -H "Authorization: Bearer {API_TOKEN}" \
  -H "Content-Type: application/json" \
  -H "x-session-affinity: user-session-abc123" \
  -d '{"messages":[
    {"role":"user","content":"Explain KV cache in one paragraph."},
    {"role":"assistant","content":"[PRIOR RESPONSE]"},
    {"role":"user","content":"Now give a concrete code example."}
  ]}'
  4. Compare latency between the two requests. The second should be faster due to prompt cache reuse. Check the cf-cache-status response header — a HIT value confirms the cache fired.
  5. Open Workers AI analytics → Cache hit rate and verify the rate climbs as you send more same-session requests with the affinity header.

What to observe

  • Measure intertoken latency on the cached vs. uncached turn — you should see a meaningful gap. If you don't, your prompt context may be too short to benefit from the KV cache (cache benefits grow with longer shared prefixes).
  • Check whether cf-cache-status: HIT appears in response headers on the second and subsequent turns — this is the direct confirmation that session affinity is working.
  • Watch your neuron consumption in the dashboard: with 80% cache hit rate, prompt-processing neurons per turn should drop substantially on long-context sessions, reducing effective cost.
