Google Fraud Defense API: three-track trust tokens for humans, bots, and AI agents

Google Fraud Defense replaces reCAPTCHA Enterprise with an API that issues cryptographically signed trust tokens separately for human users, verified bots, and AI agents — letting you write different access policies for each caller type without changing your core application logic.

Why it's worth trying: If you're building any API endpoint that AI agents will call on behalf of users, existing bot-management tools will either block the agents (treating them as bots) or require you to whitelist them entirely (bypassing fraud checks). Fraud Defense's third track — the AI agent token — lets you allow specific, authenticated agents while still enforcing fraud controls. The Agentic Policy Engine lets you write rules like "allow shopping agents from Claude or GPT; challenge everything else with high session velocity" without code deploys.

Access and pricing: Existing reCAPTCHA Enterprise customers get Fraud Defense at no additional cost — it layers on top of existing integrations with no required migration. New customers need a Google Cloud account; pricing follows the reCAPTCHA Enterprise model (usage-based, details in the Cloud Console). The Agentic Activity Measurement dashboard is available in preview to all reCAPTCHA Enterprise accounts.

Quick start — under 15 minutes if you have a GCP account

Enable the Fraud Defense API in Google Cloud Console, swap your reCAPTCHA site key for a Fraud Defense key, and make one API call to classify a synthetic session. You'll see the three-track response (human / bot / agent) in under a minute of integration work if you're already on reCAPTCHA Enterprise.

Step-by-step
  1. In Google Cloud Console, navigate to Security → Fraud Defense and enable the API for your project.
  2. Create a Fraud Defense site key — choose "Agentic Web" mode to enable all three signal tracks.
  3. Replace your existing reCAPTCHA token generation call with the Fraud Defense client SDK:
    // Browser-side (existing reCAPTCHA customers)
const token = await fraudDefense.execute(siteKey, {
  action: 'checkout',
  callerType: 'auto'  // SDK detects human / bot / agent
});
  4. On your server, verify the token and inspect the caller classification:
    POST https://frauddefense.googleapis.com/v1/projects/{project}/assessments
{
  "event": {
    "token": "TOKEN_FROM_CLIENT",
    "siteKey": "YOUR_SITE_KEY",
    "expectedAction": "checkout"
  }
}
  5. Check the response for callerClassification: HUMAN, BOT, or AI_AGENT. Write a policy rule in the Agentic Policy Engine that allows AI_AGENT traffic from your approved agent identities and challenges everything else above a risk threshold.
  6. Open the Agentic Activity Measurement dashboard and verify your test session appears correctly classified.

What to observe

  • Does your existing reCAPTCHA integration carry over without code changes, or does the SDK swap require additional configuration? The "no migration required" claim is worth verifying against your specific integration pattern.
  • Does the AI_AGENT classification fire correctly when you simulate an agent session (headless browser, API-only access, high velocity)? Check the false-positive rate on legitimate high-velocity human sessions too.
  • Confirm that the Agentic Policy Engine rule changes take effect without a code deploy — this is the key operational advantage over custom middleware solutions.

Free alternative

Cloudflare Turnstile is free for up to 1M requests/month and provides human vs. bot classification. It does not yet offer a separate AI agent track, so you'd need custom middleware to distinguish agent sessions.
