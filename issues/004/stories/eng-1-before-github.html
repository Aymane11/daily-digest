ENGINEERING PLATFORM RISK CAREER

Before GitHub: what 18 years of platform centralisation cost open source—and what Ghostty's departure signals for your infrastructure decisions

Armin Ronacher's "Before GitHub" and Mitchell Hashimoto's Ghostty departure, read together, describe the same arc: friction as a feature, centralisation as a trade-off, and the moment a platform's reliability costs exceed its convenience benefits.

BY EDITORIAL TEAM · 8 MIN READ · WED 29 APR 2026

QUICK START — DO THIS TODAY (<30 MINUTES)

Run a platform dependency audit on your team's GitHub usage. List every GitHub feature you depend on beyond git push: Actions workflows, issue tracking, PR reviews, Packages, Pages, Dependabot. For each, ask: "If this was unavailable for 8 hours today, what breaks?" The answer tells you your actual blast radius — not the theoretical one.

¶01 · THE PRE-GITHUB WORLD

Armin Ronacher describes open source before GitHub as a "much smaller world" — not worse, just different in its constraints. Projects lived on infrastructure developers controlled: self-hosted Trac installations, Subversion repositories, mailing lists. "If you wanted to publish software, you often also became a small-time system administrator."

The key property of that world was that reputation was legible. You could not depend on a library without knowing something about its maintainer, its release process, its stability. Vendoring was common because it was the only way to guarantee your dependency would be there tomorrow. The friction of establishing and consuming dependencies was high, but it was a forcing function: it made developers think carefully about what they relied on.

GitHub eliminated that friction. It democratised publishing, discovering, and contributing to open source. In doing so, it also concentrated the entire ecosystem around a single company's infrastructure—and triggered the micro-dependency explosion that has produced supply chain attacks as a predictable consequence.

¶02 · THE MOMENT THE COST FLIPS

Mitchell Hashimoto is GitHub user #1299. He has logged near-daily GitHub outages in a personal journal for years. On April 28, he announced that Ghostty — his terminal emulator — would leave GitHub over chronic reliability failures that make "serious development work" impossible.

This is the moment Ronacher's essay and Hashimoto's announcement converge: the convenience-to-friction ratio has flipped. For Hashimoto, the cost of GitHub's unreliability now exceeds the cost of managing his own infrastructure. The platform that reduced friction for 18 years is now producing more friction than the alternative.

This is a structural signal, not a personal one. GitHub's reliability problems have been episodically reported for years; this is the highest-profile departure to date. The question for engineering teams is not whether Hashimoto is right to leave. It is whether your organisation would notice the moment the same flip happened to you—and whether you have a measured answer rather than an assumption.

¶03 · WHAT FRICTION PROTECTS

Ronacher's essay makes a subtler point worth preserving: the friction of the pre-GitHub world was not purely overhead. The effort required to publish and consume dependencies created a selection pressure. Projects that survived the friction were, on average, more maintained, more stable, and more thoughtfully designed. The reduction in friction that GitHub produced also reduced the signal-to-noise ratio in the ecosystem.

The lesson is not that friction is good. It is that when you remove friction, you need to replace the selection pressure it provided with something else — code review, dependency auditing, supply chain scanning, reputation signals. The teams that did not do this in the GitHub era are the ones running npm install chains with 2,000 transitive dependencies and no understanding of what any of them do.

PLATFORM AUDIT CHECKLIST

CONCRETE RECOMMENDATIONS

01

Measure your actual GitHub outage cost

Pull the last 90 days of GitHub status incidents. Cross-reference with your team's git push and Actions timestamps. Quantify the hours lost to actual outages — not estimates.

02

Mirror critical repos to a second host

Set up a git remote mirror to Codeberg, a self-hosted Gitea, or an S3-backed bare clone. Automate it with a post-push hook. This costs less than two hours to set up and eliminates total loss risk.

03

Pin dependencies with hash verification

Replace floating version ranges with pinned hashes in your lockfiles. Use pip-compile, cargo lock, or equivalent. This is the selection pressure GitHub removed — restore it manually.

04

Define a CI fallback before you need it

Document which GitHub Actions workflows are blocking (can't ship without them) vs advisory. For blocking workflows, identify a manual or alternative CI path that can run during a GitHub Actions outage.

05

Audit your dependency reputation signals

For your ten most critical dependencies, confirm: last release date, number of active maintainers, whether the maintainer has a track record you can verify. Ronacher's pre-GitHub world had this by default; you need to reconstruct it.

06

Evaluate one self-hosted alternative

Spin up Forgejo on a cheap VPS for an internal project. This is not a commitment to migrate — it is building the muscle memory so that if you ever need to move, you know what it costs.

MODULE 06 · WHY THIS MATTERS FOR YOUR CAREER

Mental model: platform risk is operational risk

Engineers trained entirely in the GitHub era often treat GitHub as infrastructure rather than a vendor. The distinction matters: infrastructure is something you own and control; a vendor is someone who can raise prices, degrade quality, or go offline. Ghostty's departure is a reminder that every platform convenience has a corresponding dependency. Senior engineers make this trade-off consciously; junior engineers often don't know they're making it.

Bring it to your team

Run a 30-minute exercise: draw your team's dependency graph not on code, but on platforms and services. GitHub, Slack, Linear, AWS, Datadog, Stripe. For each: what is your fallback? Which ones have no fallback? The ones with no fallback are your unacknowledged single points of failure. Deciding to accept that risk is fine; not knowing you've accepted it is not.

30-day experiment

Measure: Track the number of times in the next 30 days that a GitHub outage delays your work by more than 15 minutes. At the end of the month, convert that to an hourly cost at your fully-loaded rate. If the number exceeds the cost of a redundant VPS running Forgejo, you have a quantified business case for diversification.

PLATFORM RISK TIERS

Critical: outage stops all shipping
High: outage delays deploys by hours
Medium: outage is annoying, work continues
Low: outage is unnoticed for hours

KEY INSIGHT

The engineers who will be most resilient to the next GitHub-scale platform disruption are those who understood the trade-offs they made when centralising on it — and built fallbacks proportional to the risk.
